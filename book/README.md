# PulseRisk: книга разработки проекта

Рабочее название: **PulseRisk: разработка real-time risk-management backend на .NET 10**.

Эта папка содержит книгу-практикум, которая будет писаться параллельно с реализацией проекта. Каждая глава должна соответствовать конкретному состоянию репозитория: проект можно собрать, протестировать или хотя бы проверить описанные артефакты.

## Оглавление

### Часть I. От требований к проекту

1. Зачем мы строим PulseRisk.
2. Анализ требований к демонстрируемым компетенциям.
3. Формулируем техническое задание.
4. Выбираем архитектурный стиль.
5. Планируем путь разработки.

### Часть II. Фундамент проекта

6. Создаем solution и структуру репозитория.
7. Настраиваем .NET 10, analyzers и стиль кода.
8. Проектируем доменную модель.
9. Реализуем value objects и entities.
10. Пишем первые unit-тесты домена.

### Часть III. Данные, API и транзакции

11. Подключаем PostgreSQL и EF Core.
12. Проектируем схему БД и миграции.
13. Реализуем clients, accounts и instruments.
14. Реализуем обработку сделок.
15. Обновляем позиции транзакционно.
16. Добавляем REST API и Swagger.
17. Пишем integration tests через Testcontainers.

### Часть IV. Real-time обработка и Risk Engine

18. Проектируем internal event pipeline.
19. Реализуем bounded channels и backpressure.
20. Создаем Market Data Simulator.
21. Пишем batch writer для котировок.
22. Проектируем Risk Engine.
23. Реализуем risk rule strategies.
24. Создаем risk alerts и deduplication.
25. Добавляем quote-driven risk evaluation.

### Часть V. Качество, производительность и завершение

26. Покрываем бизнес-логику unit-тестами.
27. Укрепляем integration tests.
28. Оптимизируем PostgreSQL-запросы.
29. Добавляем нагрузочный сценарий.
30. Измеряем производительность и аллокации.
31. Упаковываем проект в Docker Compose.
32. Настраиваем GitLab CI/CD.
33. Пишем README и финальную документацию.
34. Готовим проект к демонстрации на интервью.

## Правило работы

Каждая глава пишется в три прохода:

1. Черновик перед реализацией.
2. Уточнение после написания кода.
3. Финальная проверка после сборки, тестов и обновления документации.

# Глава 4. Выбираем архитектурный стиль

## Цель главы

Объяснить выбор модульного монолита с внутренней событийной обработкой.

## Основное решение

PulseRisk начинается как модульный монолит. Это позволяет показать домен, транзакционные границы, PostgreSQL и event pipeline без инфраструктурного шума микросервисов.

Внутри монолита используются слои:

- `Api`;
- `Application`;
- `Domain`;
- `Infrastructure`;
- `BackgroundWorkers`;
- `Tests`.

## Почему не микросервисы

Микросервисы добавили бы сетевую сложность, distributed transactions, deployment orchestration и observability до того, как проекту реально понадобятся эти свойства. Для учебного проекта важнее показать ясные модульные границы, которые можно вынести в сервисы позже.

## Паттерны GoF/GRASP

В этой главе появляются не GoF-паттерны, а прежде всего GRASP-принципы:

- **Low Coupling** - домен не зависит от API, PostgreSQL и фоновых workers.
- **High Cohesion** - каждый слой отвечает за свою часть: API принимает HTTP, Application оркестрирует use cases, Domain хранит бизнес-правила, Infrastructure работает с внешними деталями.
- **Protected Variations** - изменяемые части системы, например PostgreSQL implementation, quote pipeline и risk rules, будут закрываться портами и стратегиями только там, где изменчивость действительно ожидается.

Это не overengineering, потому что границы слоев напрямую нужны для unit-тестов, PostgreSQL integration tests и будущей возможности вынести workers или Risk Engine в отдельный процесс.

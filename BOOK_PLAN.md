# PulseRisk: подробный план книги по созданию проекта

Рабочее название книги: **"PulseRisk: разработка real-time risk-management backend на .NET 10"**.

Книга должна описывать создание учебно-демонстрационного проекта с нуля до завершенного репозитория так, будто автор одновременно:

- изучает исходный набор инженерных требований;
- проектирует демонстрационный fintech backend под ожидания к сильному backend-разработчику;
- пишет production-like код;
- объясняет архитектурные решения;
- фиксирует ошибки, компромиссы и улучшения;
- готовит проект к показу на техническом интервью.

Книга не должна выглядеть как сухая документация или набор сниппетов. Формат ближе к инженерному дневнику с практическими главами: в каждой главе есть задача, ход рассуждений, реализация, проверка и выводы.

## 1. Цель книги

Главная цель - показать полный путь создания проекта **PulseRisk**: от анализа требований и постановки задачи до работающего backend-приложения с Docker Compose, PostgreSQL, Risk Engine, фоновой обработкой котировок, тестами, CI/CD и performance-доказательствами.

Книга должна помочь читателю:

- понять, как из исходного набора ожиданий выделить инженерные требования;
- спроектировать backend не как CRUD, а как систему обработки событий;
- построить понятную layered architecture без overengineering;
- реализовать доменную модель fintech/risk-management системы;
- использовать PostgreSQL осознанно: schema, indexes, transactions, query plans;
- применять `async/await`, `BackgroundService`, `Channel<T>` и `CancellationToken`;
- писать тестируемую бизнес-логику;
- подготовить проект к техническому интервью;
- объяснить свои архитектурные решения на уровне уверенного backend-разработчика.

## 2. Целевая аудитория

Основная аудитория:

- C#/.NET разработчики уровня Junior+/Middle, которые хотят вырасти до уверенного backend-уровня;
- разработчики, готовящие портфолио под fintech/backend-направление;
- инженеры, которым нужно прокачать PostgreSQL, concurrency, testing и architecture;
- кандидаты, которым важно не просто "написать проект", а уметь защитить каждое решение на интервью.

Предполагаемые знания читателя:

- базовый C#;
- базовый ASP.NET Core;
- понимание REST API;
- минимальный опыт SQL;
- базовое понимание Docker.

Что книга объясняет подробно:

- почему принимается то или иное архитектурное решение;
- как раскладывать систему по слоям;
- где проходит граница домена;
- как проектировать конкурентную обработку;
- как проверять корректность через тесты;
- как мыслить производительностью и сопровождением.

## 3. Формат книги

Рекомендуемый формат: **практическая книга в 5 частях и 35 главах**.

Каждая глава должна иметь одинаковую внутреннюю структуру:

1. **Что строим в этой главе** - короткая цель.
2. **Какую компетенцию это демонстрирует** - связь с highload, PostgreSQL, multithreading, architecture, CI/CD и тестируемостью.
3. **Проектное решение** - рассуждение до кода.
4. **Пошаговая реализация** - команды, файлы, классы, миграции, тесты.
5. **Проверка результата** - `dotnet test`, HTTP-запрос, SQL-запрос, Docker, benchmark или лог.
6. **Что получилось в репозитории** - список файлов и ключевых изменений.
7. **Компромиссы и альтернативы** - что можно было сделать иначе.
8. **Вопросы для интервью** - 3-7 вопросов, которые можно обсудить по теме главы.
9. **Чек-лист главы** - краткий список done-критериев.

Такой шаблон заставляет книгу быть одновременно учебником, дневником разработки и подготовкой к собеседованию.

## 4. Стиль повествования

Тон книги:

- спокойный, инженерный, честный;
- без попытки изобразить идеальный проект с первой попытки;
- с объяснением причин, а не только результата;
- с аккуратным показом альтернатив и отказов от лишнего усложнения;
- на русском языке, с английскими техническими терминами там, где они естественны.

Важно показывать путь разработчика:

- сначала выделили требования из исходного набора ожиданий;
- затем ограничили scope;
- затем сделали простую работающую основу;
- потом усилили архитектуру;
- потом добавили конкурентную обработку;
- потом измерили и оптимизировали;
- потом оформили проект так, чтобы его было удобно защищать на интервью.

Нужно избегать:

- "магического" появления готового кода без объяснения;
- слишком больших листингов без разбора;
- микросервисов ради впечатления;
- абстрактных паттернов без связи с кодом;
- обещаний production-grade trading platform;
- имитации реального брокера или реальной торговли.

## 5. Сквозная линия GoF/GRASP

Книга должна явно показывать, что паттерны проектирования выбираются по проблеме, а не по желанию "использовать побольше паттернов".

Для каждого примененного паттерна нужно объяснять:

- **где** он находится в коде;
- **какую проблему** он решает;
- **что было бы без него**;
- **почему он не является overengineering**;
- **какая альтернатива** была рассмотрена;
- **как проверить**, что решение оправдано: тестом, dependency graph, benchmark, code review question или простотой добавления нового сценария.

Отдельный рабочий файл книги: `book/patterns-gof-grasp.md`.

Сквозная карта паттернов:

| Главы | GoF/GRASP фокус | Проблема проекта |
| --- | --- | --- |
| 4-5 | GRASP Low Coupling, High Cohesion, Protected Variations | Разделить слои так, чтобы домен не зависел от API/PostgreSQL/workers |
| 8-10 | GRASP Information Expert, Creator, Pure Fabrication | Поместить бизнес-формулы и создание объектов в понятные места |
| 11-12 | Adapter, Repository, Query Object, Unit of Work | Изолировать PostgreSQL и явно показать транзакционные границы |
| 13-17 | GRASP Controller, Command style | Не смешивать HTTP, orchestration и бизнес-правила |
| 18-21 | Producer-Consumer, Indirection, Template Method через `BackgroundService` | Развязать producers/consumers и показать controlled concurrency |
| 22-25 | GoF Strategy, GRASP Polymorphism, Simple Factory, Protected Variations | Расширять risk rules и создавать alerts без большого `switch` |
| 28-30 | Query Object, Pure Fabrication, Protected Variations | Оптимизировать только измеренные bottleneck'и |

Анти-overengineering правило: если паттерн не уменьшает связность, не повышает тестируемость, не защищает от ожидаемой изменчивости и не делает бизнес-правило яснее, он в проект не добавляется.

## 11. Правила синхронизации книги и кода

- Каждая глава должна соответствовать конкретному состоянию репозитория.
- Код из книги должен компилироваться в том виде, в котором он показан.
- Большие листинги лучше заменять ссылкой на файл и разбором ключевых строк.
- Если решение меняется в следующих главах, нужно честно объяснять почему.
- Если оптимизация появляется после benchmark, не надо "предсказывать" ее заранее.
- Если появляется временное упрощение, нужно явно помечать его как временное.
- Если глава добавляет архитектурное решение, оно должно попасть в `ARCHITECTURE.md`.
- Если глава добавляет пользовательский сценарий, он должен попасть в README.

## 14. Рекомендуемый порядок фактической работы

Оптимальный режим: писать книгу короткими итерациями вместе с кодом.

1. Написать черновик главы перед реализацией.
2. Реализовать код.
3. Запустить проверки.
4. Вернуться в главу и исправить текст по реальному опыту.
5. Добавить вопросы для интервью.
6. Зафиксировать commit/tag.
7. Перейти к следующей главе.

Так книга будет выглядеть как работа живого разработчика, который принимает решения, проверяет гипотезы и постепенно доводит систему до демонстрационного уровня.
